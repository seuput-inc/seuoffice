# 현재 제품의 중심 결함 재사용 계약

## 고정 대상

- 원본 객체 집합: 제품 `375b08bd0e1f7e8432e6514468cc9d25be01b100`의 46개 catalog, 6,121개 객체.
- 현재 객체 집합: 제품 `5e215c4910887ed4b65c241b10d64c1f978a63e3`의 같은 위치 6,121개 객체.
- 객체 식별자는 `(catalog, 원본 index, 객체 SHA256)`이다. `tools/main-diff/current-reuse-selection.mjs`의 `mutationObjectHash`는 원본 JSON을 읽은 객체의 `JSON.stringify` UTF-8 바이트를 해시한다. 키를 다시 정렬하지 않는다.
- 위치가 같아도 객체가 바뀌면 다른 변이다. 원본 실행과 그때의 MISSED·BUILD·control panic은 그대로 보존한다.

## 증거 종류

| 범위              | 실제 근거                                                     | 현재 제품 연결                                                            |
| ----------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 마지막 열 표적    | `43668835176`, 제품 5e215, 10개 job·20회 실행·고유 객체 14개  | 같은 제품의 실제 native 증거                                              |
| 앞선 24표적       | `43652914727`, 제품 ed559, 24개 job·47회 실행·고유 객체 27개  | 선택 함수 27개의 소스·어댑터·입력 생성·정규화·실행 환경 경계 증명 필요    |
| 이전 B4 완결 부분 | `43568242384`, 제품 30f303, 완결 B4 네 조각의 고유 객체 373개 | 30→f506→375→5e215의 별도 bootstrap·native API 투영·TS 참조 경계 증명 필요 |

과거 report와 inventory에는 모든 입력의 원래 JS 값이 없다. 현재 모듈을 다시 import하거나 JSON을 만들어 역사적 corpus라고 부르지 않는다. 소스 의미 동등성 증명은 역사적 입력 payload나 native/WASM 바이너리 동일성 주장과 별개다.

## 차감 경계

- 실제 raw 산출물의 앞선 엄격 감사를 통과한 완결 native 사실만 선택기에 넣는다. 선택기는 raw 감사기를 대신하지 않는다.
- 역사적 사실은 선택 함수 **전부**를 덮는 별도 소스 증명에 연결한다. 증명에는 구현 closure, 어댑터, 입력 생성, 정규화, 실행 문맥, 마지막 이름 우선 owner 매핑의 해시를 묶는다.
- `bindSelectedInventory`는 선택 함수의 `group/name/checks/single`과 등록 순서를 결속한다. 같은 이름이 다른 group에 다시 등록되면 마지막 등록이 실제 owner가 되므로 이를 하나의 이름 dictionary로 뭉개지 않는다. 사례가 늘거나 줄거나 owner·single 판정이 바뀌면 거부한다. 이 결속은 입력 payload의 동일성을 증명하지 않으며 소스 증명과 함께 소비해야 한다.
- ed559→5e215에서 선택된 24표적의 27개 함수는 기존 사례와 입력 생성이 같다. 추가 Claude·subscription 사례는 선택되지 않은 callback이고, 선택된 ChatGPT 경로는 변경된 subscription·KB 어댑터에 도달하지 않는다. 새로운 fonts·KB 함수와 이 범위 밖 변이는 이 증명으로 차감하지 않는다.
- 이전 B4의 8개 owner 정적 runtime import 그래프 272파일과 변이 구현 119파일은 30f303→5e215에서 바이트가 같다. 이 그래프가 동적 로딩 전체를 증명하지는 않는다. 별도로 `b4-pdf.ts`가 복사·import하는 `ocr.ts`와 `ocr-vision.ts`도 같은 바이트이며, 기록된 Linux에서는 Windows OCR 생성자의 플랫폼 guard가 파일 검사·spawn 전에 null을 반환한다. 공통 bootstrap은 별도 참조 도달성·기존 native API 투영으로 다룬다. 실제 로더 파일 읽기와 WASI의 random/time/console import가 없다고 주장하지 않는다.
- 시스템 글꼴 탐색을 선택한 B4 원본 index 103·106·339·341·342는 설치 글꼴·검색 순서 증거가 없으므로 차감하지 않는다. 이는 ID별 verdict 예외가 아니다. `font-locate.findSystemFont`, `font-locate.findFontCovering`, `font-similar.similarFontFor` 중 하나라도 선택한 객체는 소스 증명이 전체 selector를 덮지 못한다.
- 나머지 368개에 대한 소스 증명과 24표적의 27개 증명은 별도로 검토한다. 종전 4,398개 후보 전체를 인수한 것으로 확대하지 않는다. 불확실한 corpus·동적 소비·환경 경계는 필요한 증거 집합에 남긴다.

## 8190의 첫 차감안

- 현제품 직접 증거: 고유 객체 14개.
- 별도 소스 동등성 근거: 앞선 24표적의 27개와 이전 B4의 368개, 합계 395개. 두 경계의 독립 정적 검토에서 추가 제외 대상은 발견되지 않았다.
- 위 범위만 결속하면 현재 객체 차감안은 409개다. 같은 원본 객체는 406개, 교체 후속 객체는 3개다. 원본 네 교체의 실패 처분은 별도로 남는다.
- 나머지 5,712개는 **현재 제품 연결 증거가 아직 닫히지 않은 집합**이다. 모두 새로 실행하라는 뜻이 아니다. 다른 과거 완결 증거도 corpus·소스·환경 경계가 닫히면 그때 추가로 차감할 수 있다.
- 종전 4,398개 후보를 합격으로 승격하거나 과거 전체 실행을 성공으로 바꾸지 않는다. 실제 current 제품의 전수 감도 합격과 batch1 해제도 아직 아니다.

## 선택과 실행의 분리

선택 결과는 현재 객체의 인수 근거와 필요한 증거 집합을 정확히 분할한다. 후속 객체의 성공 수와 바이트가 같은 원본 객체의 성공 수를 따로 센다. 필요한 증거는 추가 소스 증명 또는 실제 감도 증거로 닫아야 하며, 그 집합이 곧 새 전체 행렬 실행 승인은 아니다.

계획 도구는 원본 index·control 0·원본 `% 4` 계보를 유지한다. job당 control 포함 25개 이하, 배치당 256개 이하, 최대 8병렬을 지킨다. 배치는 앞 배치의 완결 감사 뒤 순서대로만 진행한다. 현재 계약은 새 실행·전체 복구 합격·batch1 해제를 모두 `false`로 남긴다.
