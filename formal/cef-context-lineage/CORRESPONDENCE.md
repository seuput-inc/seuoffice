# Correspondence

`CreateRegistration` models the renderer's context-created process message in `src/cef_impl/ipc.rs`. `Navigate` models browser-side navigation revocation in `src/frame_navigation.rs`. `DropRegistration` and delayed `DeliverRegistration` model the pinned CEF frame contract, which does not guarantee process-message delivery during navigation. `Release` represents exact-context release and can occur after replacement.

The `NativeLineage = FALSE` model reflects the current draft's lack of an authenticated per-document identity. `NativeLineage = TRUE` is a proposed extension, not an implemented stock-CEF property: the guard models a browser-side check that the received renderer context carries the exact current native document identity. It assumes the identity cannot be forged or reused and that the browser revokes it before replacement. Neither assumption is proven by CEF's public frame identifier or the renderer message seed. Frame and CDP execution IDs are not equated. The model omits V8 script execution, browser shutdown, nonce cryptography, scheme request scheduling and CDP evaluation. No TLC run, code reproduction or proof has been performed.

Pinned Chromium 154 `WebDocument::Token()` exposes a `blink::DocumentToken` in the renderer. `RenderFrameHostImpl::FromDocumentToken(process_id, token)` requires the process identity as a second factor. Its `GetDocumentToken()` documentation forbids access while pending commit or speculative because the token may still change. `NavigationRequest::GetDocumentToken()` is documented as available only when ready to commit. A custom CEF bridge must bind the renderer's exact main-world V8 context to that browser-owned pending-commit identity before it admits synchronous document-start IPC. Waiting for committed `RenderFrameHost` state can deadlock the renderer that is blocked in synchronous IPC. The token alone is not a control-message authority, per Blink token documentation; the receiving Mojo endpoint must bind the claimed document to the real renderer process and navigation instance.

The pinned `RenderFrameHostImpl` stores pending cross-document requests in its private `navigation_requests_` map. Its `FindLatestNavigationRequestThatIsStillCommitting()` is also private and selects by recency rather than the claimed document token. The public `HasPendingCommitNavigation()` exposes only a boolean. Therefore stock CEF cannot validate the renderer's exact pending document using these APIs; a Chromium-side extension must compare the token against the relevant pending navigation on the owning RFH, with explicit cancellation and replacement handling. A renderer-provided token or latest-request lookup alone does not establish the modeled guard.

The uncompiled `0002-chromium-pending-document.patch` retains the browser-issued navigation ID, RFH token and document token at ready-to-commit, and matches either the pending request or the exact active committed document. `0003-cef-context-events.patch` sends renderer-created identities on a dedicated Mojo pipe; `0004-cef-early-context-channel.patch` binds its receiver to the originating RFH and reports candidate registration and revocation. These are not activation grants and have no runtime consumer. There is no completed off-UI request admission or shared effect gate.

`tla/ContextChannel.tla` separates two properties. `NoEffectAfterBrowserRevoke` models the requested browser-authoritative revocation boundary, assuming registration, revocation and effect serialize on one gate; the implementation does not establish that gate. `NoReleasedRegistration` is a stronger physical renderer-release property: its shortest abstract trace is SendRegister, ReleaseLocally, ReceiveRegister. The browser has not yet observed pipe closure, so that trace alone does not show an effect after browser revocation or a replacement-document relabel. Both model configurations are unrun.

Physical release without a prior navigation is possible in the pinned source: CDP `InspectorMemoryAgent::forciblyPurgeJavaScriptMemory` calls `LocalFrame::ForciblyPurgeV8Memory`, which clears the main-world window proxy; `LocalWindowProxy::DisposeContext` invokes `WillReleaseScriptContext`. See [inspector memory agent](https://raw.githubusercontent.com/chromium/chromium/154.0.8037.98/third_party/blink/renderer/core/inspector/inspector_memory_agent.cc), [local frame](https://raw.githubusercontent.com/chromium/chromium/154.0.8037.98/third_party/blink/renderer/core/frame/local_frame.cc), [proxy manager](https://raw.githubusercontent.com/chromium/chromium/154.0.8037.98/third_party/blink/renderer/bindings/core/v8/window_proxy_manager.cc), and [local window proxy](https://raw.githubusercontent.com/chromium/chromium/154.0.8037.98/third_party/blink/renderer/bindings/core/v8/local_window_proxy.cc). This is evidence of a possible physical release, not proof of a particular application's reachable CDP sequence. Exact-context evaluation still requires independent CDP context binding and revocation.

The pinned [CEF V8 API](https://raw.githubusercontent.com/chromiumembedded/cef/14c5a08/include/cef_v8.h) restricts context handles to their creating thread and requires them to be released in `OnContextReleased`; its [implementation](https://raw.githubusercontent.com/chromiumembedded/cef/14c5a08/libcef/renderer/v8_impl.cc) executes `Eval` inside the captured V8 context and refuses an invalid handle. A private native exact-context evaluator could avoid associating CEF and CDP frame identifiers, but `Eval` returns a Promise value without awaiting it when the expression produces one. Existing font registration awaits `FontFace.load()`, so a replacement must preserve Promise settlement, exceptions, by-value results and cancellation, not just dispatch a synchronous script.

`tla/NativeEvalOrdering.tla` models a distinct ordering question: an evaluation admitted before browser revocation can be delivered and execute in the still-live captured old renderer context after browser revocation but before renderer-side revocation arrives. This trace does not relabel the command to a replacement document. Result commit can be denied afterward, but this does not undo JavaScript side effects. `NoRendererEffectAfterRevoke` is expected to fail under those assumptions; `NoResultCommitAfterRevoke` assumes the browser serializes result commit with revocation. Neither model has been run, and this is not a proof that any specific transport follows that ordering.

`tla/NativePromise.tla` models request claim, reentrant serialization, exact-context release and cancellation; the renderer-thread `PendingEvaluations` draft in `src/cef_impl/native_eval.rs` represents pending/settling requests with instance-qualified nonces and calls completions only after dropping its borrow. Release removes matching requests before calling their stale completions. The model assumes renderer-thread serialization and abstracts away V8, Mojo, browser authority and result delivery. It and the Rust regression source are unrun, and the state machine is not connected to a V8 handler or transport.

`tla/NativeSubscription.tla` models a registry-serialized owner-loss subscription, revocation claim, handle drop and callback dispatch outside the lock. It corresponds to the uncompiled `NativeContextToken::on_revoke` draft: a failed nonblocking subscription must be interpreted as already lost, and a handle dropped after callback claim cannot stop that callback. It does not prove that all native invalidation events reach the registry; the authenticated CEF lifecycle producer is not yet connected.
